# M1 - The warrior always comes back

Status: **in progress** (T01 merged; queue in `docs/tasks/README.md`, tracker
in [issue #1](https://github.com/diegoami/neowarrior-borg/issues/1)).
Proposed tag: `v0.1.0`.

## The goal

A Borg that births its own warrior - a race from the measured shortlist and a
point-buy computed from the real cost tables - plays it as far as it can, and
when it dies starts the next identical warrior unattended. Every run is
recorded. The milestone ends with the fork's first measured statement: which
candidate race goes deepest, over a fixed seed set, as the default.

## The problem this solves

The stock host reincarnates an autoplayer by rolling a **random race and
class** with roller stats (`reincarnateAutoplayer` in the game's `main.ts`;
the engine's `game.reincarnate` accepts `raceName`/`className` but the host
passes neither). A warrior project cannot stand on that. Every seam the fix
needs already exists in the published mod API, all landed by game 1.19-1.22:

| Seam | What it gives us | Game issue |
| --- | --- | --- |
| `birth(ctx)` under `ui:birth.replace` | character creation as a draft the mod edits through the game's own point-buy rules and accepts | neo-angband#291 |
| `onDeath: "end"` + `ctx.saves.create({ resumeAutoplayer: true })` | the ordinary death flow, then the next character born straight back under our controller | neo-angband#300 |
| `ctx.character.onRunEnd` / `key()` | the report each death produces, and storage for the journal | neo-angband#291 |
| manifest `settings` (numeric) | `raceChoice` as a number the player can move | neo-angband#362 |

No engine changes. The headless harness mirrors the same build through
`startGame({ raceName, className: "Warrior", birthStats })`, so the mod and
the measurement share one plan module (T02).

## Non-goals (M1)

- **No decision-code changes.** The ladder, danger and power code stay
  upstream-faithful; divergences are M2, each with a run record (rule 1/3).
- **No win condition work.** "As far as possible" is measured as depth; what
  to do about Morgoth is a later milestone's question.
- **No screen recording** (owner decision, #1); records are the in-mod
  journal plus committed tables.

## Acceptance

1. An unattended headless session of at least three consecutive characters is
   entirely the planned warrior - asserted from the born player, not our
   bookkeeping (T04).
2. A human creating a character the ordinary way is never interrupted by the
   fork's birth (T03's no-flag decline).
3. Every session leaves `docs/runs/<date>-<label>/` with harness-written JSON
   and a curated table (T06); the bake-off's table names the default race
   (T07).
4. `pnpm verify` green on the candidate; the only permitted red is the
   recorded upstream play-harness failure (#12, rule 6).
5. Milestone review per `docs/process.md` §4; tag on exactly the reviewed SHA.

## Measurement strategy

The play harness (boots the published engine, content from the sibling game
checkout) is the repeatable instrument; a watched desktop run is the
acceptance instrument for "does it actually do this in the real window" - one
`watched.md` before tagging. Races are compared across the **same seeds**,
medians over runs, `maxDepth` / `clvl` / deaths-in-town / command census as
the standing metrics (`docs/runs/README.md`).

## Risks

- **The presenter hijacks a human's birth** - mitigated by the one-shot flag
  consumed per birth and tested both ways (T03); it is the milestone's worst
  failure mode because it is the one a player would hit.
- **The reload loop leaks the flag** - a flag set but never consumed means the
  *next* human character is born as a warrior; the flag is cleared on
  consume, decline and cancel paths (T03/T04 tests).
- **`create()` fails at runtime** (storage, host refusal) - contained as a mod
  fault, the run ends rather than loops (T04).
- **Bake-off noise** - a lucky seed picks the wrong default; same seeds per
  race, medians argued, owner decides (#1 decision owed).
