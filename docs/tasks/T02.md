# T02 The warrior build plan, as a pure module

- **Kind**: feature
- **Issue**: #3 · **Branch**: `task/T02-build-plan` · **Merge after**: T01
- **Owns**: `src/birth/plan.ts`, `src/birth/plan.test.ts`.
- **Scope**: A pure, game-free module that computes the warrior's birth from a
  catalogue-shaped input: pin class **Warrior**, take the race as a caller
  setting, and compute the point-buy allocation with a deterministic priority
  (STR, then CON, then DEX; INT/WIS last) under the real cost and refund
  semantics. It must fully spend the budget when spending is legal, never
  propose an illegal step, and expose the allocation as base-stat targets the
  birth session's `buy`/`sell` can reproduce exactly. Input types mirror the
  `Api2BirthCatalogue`/`statCosts` shapes so the presenter (T03) and the
  headless harness (`startGame({ birthStats })`) are two callers of one plan.
  Out of scope: the roller, name/history/background, any decision code.
- **Done when**:
  1. `pnpm vitest run src/birth/plan.test.ts` covers every race in the real
     content pack (skip out loud without the sibling checkout, like
     `src/play.test.ts`): each allocation is legal, spends the budget, and
     honours the STR>CON>DEX priority given that race's adjustments.
  2. A case with the Half-Troll adjustments produces base 18 STR for total
     cost within the stock point budget (the pack's numbers, asserted, not
     assumed).
  3. `pnpm verify` is green.
- **Hazards**: inventing a cost model. The game's cost/refund rules come from
  the session (`draft().statCosts`) and the engine's `pointBuyCost`; the module
  must be handed those tables, never re-derive them differently (rule 4).
