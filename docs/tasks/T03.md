# T03 The birth presenter: the mod births its own warrior

- **Kind**: feature
- **Issue**: #4 · **Branch**: `task/T03-birth-presenter` · **Merge after**: T02
- **Owns**: `src/birth/presenter.ts`, `src/birth/presenter.test.ts`, the
  `birth` member of the plugin definition in `plugin.ts`.
- **Scope**: Register a `birth(mod)` presenter under the already-declared
  `ui:birth.replace`. When a one-shot flag in the mod's install slot is set
  (set by the title row in T05 and by the restart loop in T04), `show(session)`
  builds the warrior through the session's own rules - `chooseRace`,
  `chooseClass("Warrior")`, point-buy to T02's plan, `accept()` - consuming the
  flag so exactly one character is created per flag. With no flag, the
  presenter declines (`undefined`) and the game shows its own screens: **a
  human creating a character is never hijacked.** A catalogue race the plan
  names but the pack does not define declines and logs, rather than birthing a
  wrong character. Out of scope: the restart loop, the title row's flag-set.
- **Done when**:
  1. `pnpm vitest run src/birth/presenter.test.ts` drives a fake
     `Api2BirthSession`: with the flag, exactly one accepted character whose
     race/class/stats equal the plan's, and the flag is consumed; without the
     flag, no session method is called.
  2. The same fake covers the unknown-race decline (log + no accept + flag
     consumed, so the loop cannot spin on it).
  3. `pnpm verify` is green, and `src/manifest-capabilities.test.ts` still
     derives the capability list from source (it must now include
     `ui:birth.replace` because `birth()` exists).
- **Hazards**: answering `show` with work that outlives it (the presenter must
  complete synchronously from `catalogue()`/`draft()` data; nothing async
  between flag-read and accept), and defaulting the race from the catalogue
  order rather than the caller's setting.
