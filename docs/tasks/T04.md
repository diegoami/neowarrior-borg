# T04 The unattended restart loop: every death, the same warrior

- **Kind**: feature
- **Issue**: #7 · **Branch**: `task/T04-restart-loop` · **Merge after**: T03
- **Owns**: `src/loop/restart.ts`, `src/loop/restart.test.ts`, the controller
  install shape in `plugin.ts`, the harness loop in `src/play.test.ts` (its
  warrior variant).
- **Scope**: Replace the default reincarnation - the stock host rolls a random
  race and class, which is precisely what this fork exists not to do. The
  controller installs with `onDeath: "end"`; at `ctx.character.onRunEnd` the
  mod sets the birth flag (T03) and calls `ctx.saves.create({ resumeAutoplayer:
  true })`, so the page reloads into birth, the presenter builds the same
  warrior, and the controller retakes the keyboard without a prompt. Guard the
  call: only when the mod's controller held the keyboard, and never with
  `like`'s birth overriding the plan. In the headless harness (no web shell,
  no page reload), the same loop is approximated by booting the next character
  with `startGame({ raceName, className: "Warrior", birthStats })` from the
  same plan - the exact build the presenter produces.
- **Done when**:
  1. `pnpm vitest run src/loop/restart.test.ts` covers: a run report while
     holding the keyboard → flag set and one `create({ resumeAutoplayer: true
     })`; not holding it → nothing; a `create` failure → the fault is
     contained (no unhandled rejection) and the run ends without a loop.
  2. The headless harness plays a session of at least 3 consecutive warriors -
     deaths included - and every character in it is the planned Warrior build
     (race and base stats asserted from the live player, not from our own
     bookkeeping).
  3. `pnpm verify` is green.
- **Hazards**: calling `create()` from anywhere but `onRunEnd`'s report path,
  and trusting the mod's own memory of the build instead of asserting it from
  the born player (the stock borg's history is full of seams that wrote
  nothing; the harness must read the live character).
