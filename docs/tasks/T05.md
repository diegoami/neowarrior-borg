# T05 The title row arms the warrior, and a setting picks the race

- **Kind**: feature
- **Issue**: #8 · **Branch**: `task/T05-title-and-settings` · **Merge after**: T03
- **Owns**: `title.ts`, `title.test.ts`, `manifest.json`'s `settings` key,
  `src/birth/settings.ts` (+ tests), `SETTINGS.md`, `docs/README.md`.
- **Scope**: The title row "New Warrior Borg character" (label already
  rebranded) sets the birth flag before its `create-character` action, so a
  character started from the row is born as the planned warrior (the row was
  already the player's consent in upstream's design). Add the mod's first
  numeric settings under the manifest's `settings` key: `raceChoice`, an index
  over the documented candidate list (0 Half-Troll, 1 Dunadan, 2 High-Elf,
  3 Dwarf - the T07 bake-off shortlist), consumed by the presenter through a
  small resolver that clamps via `resolveSettingValue` and falls back to the
  first candidate when the pack lacks the named race. The candidate list is a
  named constant with its rationale in the source, not a magic array.
- **Done when**:
  1. `pnpm vitest run title.test.ts` shows the row's action sets the one-shot
     flag (and the existing profile behaviour is unchanged).
  2. `pnpm vitest run src/birth/settings.test.ts` covers: index → candidate,
     out-of-range index → clamped by the declared min/max, unknown-to-pack race
     → fallback to the first candidate, log line naming what was chosen.
  3. `pnpm verify` is green, including `docs-sync.test.ts` against the updated
     `docs/README.md` and `SETTINGS.md`.
- **Hazards**: a setting the presenter reads at the wrong moment. The race is
  resolved once per birth, at `show`, from the then-current value - not cached
  at mod start, or a settings change would silently not apply to the next
  warrior.
