# T06 Run records: the journal inside the mod, the tables outside it

- **Kind**: feature
- **Issue**: #7 · **Branch**: `task/T06-run-records` · **Merge after**: T04
- **Owns**: `src/records/journal.ts`, `src/records/reporter.ts`, their tests,
  the `event:dungeonlevel` declaration, `docs/runs/` tooling (`tools/runs.mjs`
  if a writer is needed).
- **Scope**: Both halves of the recording requirement. In the mod: a journal
  under `ctx.character.key()` - depth milestones from the `dungeonlevel` event
  (the documented pattern for exactly this), and at each `onRunEnd` a graveyard
  entry (build, max depth, character level, gold, turns, cause of death, final
  score) written before T04's restart call so a crash in `create` cannot lose
  the record. Outside: one reporter the headless harness calls, emitting the
  `runs.json` schema of `docs/runs/README.md` (one entry per character, command
  census included) plus the session's build facts, so T07's tables and any
  later regression comparison are generated, never hand-assembled.
- **Done when**:
  1. A test plays a short headless session through at least one death and one
     rebirth and asserts: the journal holds the depths actually visited (read
     from the live game), the graveyard holds one entry per dead warrior with
     the killer the game reported, and the reporter's JSON validates against
     the schema (field-by-field assertions, not a snapshot of our own output).
  2. A depth milestone is recorded exactly once per level per character (the
     event also fires on load with `cause: "load"` - the dedup rule).
  3. `pnpm verify` is green; a session's `runs.json` is committed under
     `docs/runs/` from this task's harness run, per rule 1.
- **Hazards**: writing the journal after triggering the reload (the record is
  lost to the page teardown), and trusting the mod's own view of depth instead
  of the event payload.
