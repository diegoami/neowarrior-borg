# T09 A random suited race for every warrior

- **Kind**: feature (owner directive, 2026-11-02)
- **Issue**: #33 · **Branch**: `task/T09-random-race` · **Merge after**: T07
- **Owns**: `src/birth/settings.ts` (+tests), the manifest's `rules`/
  `settings` additions, `SETTINGS.md`, `docs/README.md`, the install-slot
  lineage counter, `src/birth/presenter.ts` only if its wiring must see the
  drawn race's log line.
- **Scope**: By default each birth draws ONE RACE UNIFORMLY from the suited
  shortlist (WARRIOR_RACE_CANDIDATES: Half-Troll, Dunadan, High-Elf, Dwarf),
  instead of always playing `borg.raceChoice`. The draw is DETERMINISTIC
  (rule 4): no wall clock, no game RNG, and the borg's decision RNG stays
  untouched - a persisted birth counter in the install slot (`lineage`,
  incremented at each draw) seeds a one-draw hash, so the same session state
  always yields the same sequence while every reload still varies the race.
  A new toggle `borg.raceRandom` (default ON, per the owner) gates it; with
  it off, `borg.raceChoice` pins the race exactly as today. Every automated
  birth logs which race was drawn and why (the counter and the shortlist
  size), so an unattended run's record says what it played. The shortlist
  itself is confirmed by T07's data: the owner may trim a race that measures
  as dead weight before v0.1.0 is tagged.
- **Done when**:
  1. `pnpm vitest run src/birth/settings.test.ts` covers: raceRandom on ->
     draw varies across successive births and stays inside the shortlist;
     the SAME persisted counter state produces the SAME draw (determinism);
     raceRandom off -> raceChoice honored exactly as before; the counter
     survives a simulated reload (slot round-trip); sibling keys preserved.
  2. The birth presenter's existing tests stay green with raceRandom
     defaulting on in cfg (the harness passes explicit races; nothing
     there changes).
  3. `pnpm verify` green except the recorded upstream #12; `pnpm check`
     current; SETTINGS.md/docs-README tables updated and `docs-sync`/settings
     tests green.
- **Hazards**: drawing from the borg's decision RNG (load-bearing pacing -
   T05 found its await-count is pinned by tests; use the counter hash, not
   that stream) and letting the counter and the graveyard disagree (the
   journal remains the record of what WAS played; the counter only feeds
   the draw - say so in both headers).
